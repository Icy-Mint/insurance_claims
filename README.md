# SOP-Guided Insurance Claims Agent

A conversational agent for insurance claims support built around a **deterministic
state machine** that gates what the LLM is allowed to do. The LLM only ever handles
natural-language understanding (extraction) and phrasing (response generation) —
it never decides what phase the conversation is in, and it is structurally unable
to look up claim details before the caller is verified.

## Architecture

```
caller message
      |
      v
 extraction pass  (regex/keyword cascade; optional LLM enrichment)
      |            -> PII candidates, intent/case hints, sentiment,
      |               consent, in/out-of-scope, refusal signals
      v
 apply to session state (pii_candidates, memory, sentiment_history, ...)
      |
      v
 deterministic phase handlers + next_phase()   <-- plain Python, not LLM
      |            VERIFY_ID -> RESOLVE_INTENT -> PROCESS_CASE -> POST_PROCESS
      v
 response-generation pass (phase-specific system prompt + tool results)
      |            claim-lookup tool *definitions* are only included in the
      |            request once state.verified == True
      v
 reply + phase + ui_hints
```

- **`app/models.py`** — the `SessionState` dataclass and the `Phase` enum. This is
  the single source of truth for a conversation.
- **`app/extraction.py`** — the cheap, regex/keyword extraction pass that runs every
  turn regardless of phase. This is what lets the agent stash "denied healthcare
  claim from January" while the caller is still being verified.
- **`app/phases.py`** — `next_phase()`, the deterministic transition function, plus
  the per-turn orchestration that runs phase handlers and the cascade.
- **`app/tools.py`** — the fixed tool layer over the fixture JSON. Nothing here ever
  takes an LLM-generated query; `get_claim_detail` etc. only take IDs the backend
  itself resolved deterministically.
- **`app/llm.py`** — Anthropic API integration and the **capability gate**:
  `build_tool_defs(state)` returns `[]` (no claim-lookup tools at all) until
  `state.verified` is `True`. `execute_tool()` additionally hard-refuses those calls
  if verification is somehow bypassed, as defense in depth.
- **`app/templates.py`** — deterministic fallback replies, used whenever
  `ANTHROPIC_API_KEY` isn't set (or a live call fails), so the app and the whole
  test suite work fully offline. Real Claude output only ever changes *phrasing*;
  the facts asserted on in tests come from the tool layer either way.
- **`app/prompts.py`** — phase-specific system prompts for the real-LLM path.

### Two-pass-per-turn

1. **Extraction pass** (`extraction.extract_signals`): a regex/keyword cascade
   covers the majority case (dates, SSN/ID fragments, policy numbers, sentiment
   keywords, yes/no, obvious in/out-of-scope). `llm.llm_extract_enrich` optionally
   asks Claude to fill in gaps when regex found nothing during `VERIFY_ID` — it can
   only *add* fields regex missed, never override what regex already found, so
   phase transitions stay deterministic even when the LLM enrichment step runs.
2. **Response-generation pass** (`llm.generate_reply`): a phase-specific system
   prompt plus already-computed tool results produce the caller-facing reply. For
   `PROCESS_CASE`, if a live Claude client is configured, the model is given the
   `get_claim_detail` / `get_required_documents` tool definitions (only once
   verified) and must call at least one before it's allowed to answer — the code
   forces a retry if the model tries to answer ungrounded. Every fact in a
   `PROCESS_CASE` reply is therefore traceable to a tool return value.

### Why phases can cascade within a single turn

The Margaret Chen test message contains identity fields *and* the case hint in the
same sentence. Rather than needing four separate replies, `process_turn` re-applies
`next_phase()` after each deterministic handler runs, so verification, intent
resolution, and the claim lookup can all complete in one turn when the caller
happens to give everything at once — while still refusing to skip any gate if the
data isn't there yet.

## Setup

### Environment variable

The backend reads `ANTHROPIC_API_KEY` from the environment. **It is optional**:
without it, every reply is generated by the deterministic template layer instead
of live Claude output — useful for offline development and for running the test
suite. Model id defaults to `claude-sonnet-5`, overridable via `ANTHROPIC_MODEL`.

To use a real key locally, copy `backend/.env.example` to `backend/.env` and put
your key in there yourself — `backend/.env` is git-ignored and the app loads it
automatically (`app/main.py` calls `load_dotenv()`), so the key never needs to be
typed anywhere else. The test suite explicitly strips `ANTHROPIC_API_KEY` from the
environment before running (stashing the original value rather than discarding it —
see `real_llm` below), so a local `.env` never affects the deterministic majority
of `pytest`.

### Run locally without Docker

Backend:

```bash
cd apps/insurance_claims/backend
python -m venv .venv
source .venv/Scripts/activate   # Windows Git Bash; use .venv/bin/activate on macOS/Linux
pip install -r requirements.txt
export ANTHROPIC_API_KEY=sk-ant-...   # optional
uvicorn app.main:app --reload --port 8000
```

Frontend (separate terminal):

```bash
cd apps/insurance_claims/frontend
npm install
cp .env.local.example .env.local   # NEXT_PUBLIC_API_BASE=http://localhost:8000
npm run dev
```

Open http://localhost:3000 (redirects to `/chat`).

### Run via Docker

```bash
cd apps/insurance_claims
ANTHROPIC_API_KEY=sk-ant-... docker compose up --build
```

or individually:

```bash
# from apps/insurance_claims/ so both backend/ and fixtures/ are in the build context
docker build -f backend/Dockerfile -t insurance-claims-backend .
docker run -p 8000:8000 -e ANTHROPIC_API_KEY=sk-ant-... insurance-claims-backend

cd frontend
docker build --build-arg NEXT_PUBLIC_API_BASE=http://localhost:8000 -t insurance-claims-frontend .
docker run -p 3000:3000 insurance-claims-frontend
```

(`NEXT_PUBLIC_API_BASE` is inlined into the client bundle at build time, so it's a
build arg, not a run-time `-e` flag.)

> Docker wasn't available in the environment this was built in, so the images
> were reviewed but not build-verified end to end — please flag if `docker build`
> surfaces anything.

## Running the tests

```bash
cd apps/insurance_claims/backend
source .venv/Scripts/activate
pytest -v
```

The large majority of the suite runs entirely offline (no network, no API key)
against the deterministic fallback path, so grading doesn't depend on Anthropic
API availability. A small number of tests opt into a real live-model call via the
`real_llm` fixture (see below) and skip themselves gracefully if no key is
configured:

- **`tests/test_margaret_chen_happy_path.py`** — the spec's primary scenario: a
  single message containing identity fields *and* the claim hint. Asserts exactly
  3 countable fields verify (`full_name`, `dob`, `ssn_last4` — `policy_number` is a
  lookup key, not counted), the hint resolves to `CL-2048` without re-asking, the
  reply is grounded only in `CL-2048`'s facts (denial reason, missing documents,
  appeal deadline) with no leakage from the caller's other claims, and the email
  summary is only sent after an explicit "yes". Also covers the incremental
  partial-answer case (phase stays `VERIFY_ID` until the 3rd field arrives).
- **`tests/test_frustration_deescalation.py`** — the spec's frustration scenario:
  acknowledges feelings, explains the gate, offers alternatives, and never leaks
  claim facts or skips verification, including under repeated friction (which
  triggers a human-transfer offer without ever bypassing the gate).
- **`tests/test_capability_gating.py`** — unit-level checks that claim-lookup tool
  *definitions* are absent from the LLM request before verification, and that the
  tool executor refuses to run them even if called directly.
- **`tests/test_scope_and_escalation.py`** — off-topic redirection, the
  2-consecutive-off-topic-turns human-transfer offer, the counter resetting on
  an in-scope reply, and a refusal during `VERIFY_ID` not verifying anything.
- **`tests/test_consolidated_state_suite.py`** — the canonical regression suite for
  the six root-cause bugs found across several rounds of adversarial testing (the
  LLM narrating a verification/send/transfer that didn't structurally happen).
  13 tests, each asserting on `debug_state` fields from the `/chat` response or a
  monkeypatched spy on the real tool function — **never** on parsing reply text —
  so a well-worded hallucination of an action can't pass a test that only a real
  state change should satisfy. This is the file to extend first when a new bug of
  this shape turns up. Three of the thirteen (intent-hint carryover, compound
  "yes + transfer" parsing, frustrated-but-on-topic classification) use the
  `real_llm` fixture below instead of the deterministic fallback, since they're
  specifically about messy natural-language understanding.

### The `real_llm` fixture

Most of the suite runs against the deterministic template fallback (see above) —
fast, free, and immune to model non-determinism. A few tests need to exercise a
genuine live model call instead; they take the `real_llm` fixture (defined in
`tests/conftest.py`), which temporarily restores a real `ANTHROPIC_API_KEY` (from
a repo secret in CI, or `backend/.env` locally) and resets `llm.py`'s cached
client, then restores the offline state afterward so no other test is affected.
If no key is available anywhere, the fixture **skips** those tests rather than
failing the run — so the suite stays green in an environment with no API key
configured, and automatically exercises the real model wherever one is available.

## Continuous integration

`.github/workflows/backend-tests.yml` runs the full backend suite on every push
and pull request that touches `apps/insurance_claims/backend/**` or
`apps/insurance_claims/fixtures/**`. Set the `ANTHROPIC_API_KEY` repository secret to
also run the `real_llm`-backed tests in CI; leave it unset and the workflow still
passes, with those three tests skipped.

## Manual test coverage (also exercisable in the UI)

- **Partial ID answers**: give one field at a time (`My name is Margaret Chen.` →
  `My date of birth is 1985-03-15.` → `Last four of my SSN is 4472.`) and watch the
  phase badge stay on "Verifying identity" until the third field lands.
- **Refusals**: `I'd rather not share my SSN.` — the agent should ask for an
  alternate field instead of pressuring the caller, and never verify from it.
- **Out-of-scope questions**: `What is RL?` gets politely redirected; two in a row
  surfaces a "Transfer me to a human" quick reply.
- **Representative / consent flow** (David Chen calling for Margaret Chen, P9): the
  `check_representative` and `get_consent_status` tools exist in `app/tools.py` for
  this path; it's wired up for manual exploration but isn't asserted by the
  automated suite.

## Design notes / trade-offs

- **Capability gating is structural, not prompt-based.** `build_tool_defs` never
  includes `get_claim_detail` / `get_required_documents` in the request sent to the
  model until `state.verified` is `True`, and the tool schemas take no arguments —
  the backend always injects the deterministically-resolved `case_id`, so even a
  jailbroken model can't ask for a different caller's claim.
- **Determinism over LLM judgment for phase transitions.** `next_phase()` reads
  `verified_fields`, `memory["resolved_case_id"]`/`resolved_intent`, and
  `memory["case_query_resolved"]` — the last of these is set the moment a claim
  lookup tool actually returns data, not by the LLM's opinion that it has "enough"
  information.
- **Offline-first testing.** Because the fallback template layer performs the same
  tool calls and grounding rules as the live-LLM path, the automated tests validate
  the SOP-enforcement logic itself rather than incidentally testing Claude's
  compliance with a prompt.
